# Manual M2/M3 QA and publication regression

Date: 18 October 2026 (Asia/Kolkata).

Tested the local working tree on `feature/wedding-website-events`, including uncommitted M3 work. No checkout of `origin/develop`, application-code edits, commit, push or production deployment was performed by this QA run.

## Publication fix: verified

The original issue was reproduced before the owner's fix: publish from Preview, return to settings, see “Draft · private,” then encounter a revision conflict on save. Explicit reload recovered the editor.

After the owner supplied the fix, rebuilt the workspace and loaded the new frontend. With real Atlas persistence in the isolated QA environment:

1. Unpublished the synthetic wedding and confirmed draft settings.
2. Opened saved Preview and published it.
3. Returned using **Back to website settings**, without reloading.
4. Settings immediately displayed **Published**, **Open guest website** and **Unpublish**.
5. Edited Introduction and saved without reloading. The save succeeded with “Website saved. Your changes are now live.” No revision conflict appeared.
6. Opened the guest route through the client and confirmed the saved introduction appeared.
7. Opened a second settings tab, entered unsaved text, saved a competing change from the first tab, then submitted the stale tab. The genuine conflict was rejected, the stale text remained, and explicit reload/discard was offered.

Result: **publication regression passed; genuine conflict protection and entry retention remain intact.**

`npm run test:client -- client/src/features/website/website.test.tsx` passed all seven targeted component tests, including the regression that holds the background settings GET pending. `npm run build` passed after the fix. The owner's separately recorded full-suite results are historical evidence, not a full-suite rerun by this QA session.

## Remaining findings and limits

- Known signup missing-date wording (“Invalid ISO date”) remains reproduced. Duplicate-email feedback duplication remains a previously known issue; this run verified duplicate prevention by HTTP rather than rechecking that exact UI presentation.
- **Low: last-ceremony archive guard wording.** On a published wedding with one active ceremony, confirm its archive. The operation is correctly rejected, but says “Add at least one ceremony before publishing.” Prefer an instruction to add another ceremony or unpublish before archiving the last one.
- Mobile viewport override was attempted again, including a newly created tab. DOM measurements remained 1280 pixels wide instead of the requested 390; the override was reset. This run does not verify mobile layout, despite historical mobile browser checks recorded elsewhere.
- Separate focus/visibility-return refresh, exact 25-second timing, large lists/pagination, referenced-record archive confirmation, DST edge cases, service-outage save/refresh recovery, long session expiry, production HTTPS/proxy settings and real Resend delivery were not manually covered in this run. Existing automated coverage must not be presented as fresh manual evidence.
- Rebuilding in place while the isolated server was running left its already-cached public HTML referencing old asset names. The rebuilt publication fix was tested using fresh private-page loads and client navigation to the guest route; a new-process public HTML smoke test after that rebuild was not performed.
